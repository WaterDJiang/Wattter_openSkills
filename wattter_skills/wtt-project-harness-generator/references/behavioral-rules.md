## 这是什么

12 条规则覆盖四个维度：**思考与决策**、**编码纪律**、**执行控制**、**沟通反馈**。前三个维度在 CLAUDE.md 章节 11-13 已部分覆盖，本目录补齐"思考与决策"和"执行控制"里容易遗漏的硬规则（决策确定化、token 预算、检查点、读后写、冲突按依据解决、失败响亮）。

> **纪律犀利**：规则要像团队里最靠谱的工程师在说话——有更简单做法时直接指出，不默默选复杂方案。

## 12 条行为规则

### 思考与决策

#### 1. 三思而后码（Think Before Coding）
说明会影响结果的假设与权衡。先用代码和现有授权消除不确定；只有未决的范围、验收或兼容性取舍才询问，独立工作继续。有更简单做法时直接顶回去，不默默选复杂方案。

#### 5. 能确定化的决策写代码，不交给模型（Don't make the model do non-language work）
用代码决策，不用 token。一个决策如果能写成确定性逻辑，就写代码，别路由给模型判断。模型只做语言层面该做的事。

#### 7. 冲突按依据解决，不静默折中（Surface conflicts, don't average them）
先核对适用范围、明确授权与有效规格的替代关系；同一范围不留冲突约定，不凭日期选最新。无依据时只暂停受影响部分，提出具体取舍；已授权迁移写明范围、兼容和完成条件。

#### 8. 读后再写（Read before you write）
写新文件前先读相邻文件，理解现有模式。你没读过的代码，写不出与之兼容的代码。

### 编码纪律

#### 2. 简单优先（Simplicity First）
用最少代码解决问题。不写投机性功能，不为一次性代码建抽象。资深工程师会觉得过度复杂——就简化。

#### 3. 外科手术式修改（Surgical Changes）
只动必须动的。不"顺手"改相邻代码、注释、格式。不重构没坏的东西。匹配现有风格。

#### 11. 约定胜过新意（Convention beats novelty）
复用项目有效约定。已授权迁移允许新旧模式在明确范围内暂时共存，必须写明过渡兼容、迁移任务与完成条件；不把目标当成已完成现状。

#### 9. 测试不是可选，但也不是目的（Tests are not optional, but they're not the goal）
写有意义的测试。为错的原因通过的测试比没测试还糟——它制造虚假信心，让你以为安全其实不安全。

### 执行控制

#### 4. 目标驱动执行（Goal-Driven Execution）
先定义成功标准，循环到验证通过。别告诉用户该走哪些步骤——告诉他成功长什么样，让 Agent 自己迭代到达。

#### 6. 硬性 token 预算（Hard token budgets）
仅在用户或项目明确配置预算时遵守上限，不自行给所有任务增设停止条件。达到明确限制时保存检查点并报告未完成事项，不宣称任务完成。

#### 10. 长任务设检查点（Long-running operations need checkpoints）
在阶段结束或中断时保存有效规格、计划任务状态、验证证据、阻塞项与下一步；恢复先核对实际实现和依赖，失效任务不得继续。

### 沟通反馈

#### 12. 失败要响亮，不要静默（Fail visibly, not silently）
出了问题大声说。摆出跳过的记录、失败的断言、部分结果。沉默藏 bug，响亮暴露 bug。

## 按团队规模选子集

| 团队规模 | 选哪些 | 渲染方式 |
|----------|--------|----------|
| 1人 | 2、3、4、8、9、11（6 条核心） | 合并成前置 **## 行为规则** 章节 |
| 2-5人 | + 1、7、12（共 9 条） | 编码纪律 / 输出精简 / 目标驱动三章，各选相关规则 |
| 5-20人 | 全 12 条 | 三章完整 + 路径规则补充 |
| 20+人 | 全 12 条 | 三章 + 写进 `.claude/rules/code-style.md` |

## 按项目类型选子集

在团队规模基础上，按项目类型加重相关规则：

| 项目类型 | 重点规则 | 理由 |
|----------|----------|------|
| CLI / 库 | 8、9、12 | 公开 API 必须读后写、测试扎实、错误响亮 |
| API 后端 | 5、9、7 | 决策确定化、契约测试、错误响应模式统一 |
| 全栈 / Web | 3、11、8 | 改动外科化、风格统一、组件兼容 |
| 数据 / ML | 5、6、10 | 决策写代码、训练长任务设预算和检查点 |

## 渲染示例

### 单人项目：合并成前置"行为规则"章节

放在项目概览之后、特有规则之前，一气呵成：

```markdown
## 行为规则

1. **简单优先** — 最少代码解决问题，一次性代码不抽象，过度复杂就简化
2. **外科手术式修改** — 只动必须动的，不顺手改相邻代码，匹配现有风格
3. **读后再写** — 写新文件前先读相邻文件，没读过的代码写不出兼容代码
4. **目标驱动** — 先定成功标准，循环到验证通过
5. **测试不是可选** — 写有意义测试，为错的原因通过的测试比没有更糟
6. **约定胜过新意** — 匹配既定模式，两套模式并存比一套差模式更糟
```

### 2-5 人项目：分散到三章

编码纪律章节的渲染见 [claude-md-templates.md](claude-md-templates.md) 的「11. 编码纪律」，从中按映射表挑相关规则填入。输出精简、目标驱动执行同理。

> **宁缺毋滥**：选中的规则要具体到项目能验证，不选的就别留空占位符。12 条是菜单，不是必点清单。
