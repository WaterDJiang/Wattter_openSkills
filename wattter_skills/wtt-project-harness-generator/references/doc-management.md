# 项目文档管理规范

> plan/log 会日益增长，单文件会让每次上下文爆掉。本规范用 **分类 + 索引 + 分片 + 渐进式读取** 管理整个项目的文档，让 LLM 按需读、不全量加载。

## 一、核心原则

**索引 + 分片 + 按需读**——每个会增长的文件夹都有一个 INDEX，LLM 先读 INDEX 看全貌和最近结论，按 INDEX 指针读需要的分片，不把整份历史塞进上下文。

```
项目根/doc/
├── INDEX.md          # 项目文档总索引：列所有分类文件夹 + 一句话用途 + 指针
├── spec/             # 规格（需求/产品定义）
│   └── INDEX.md
├── plan/             # 计划（开发/实施计划）
│   └── INDEX.md
├── log/              # 执行日志（每日/每次工作）
│   └── INDEX.md
├── design/           # 设计文档（架构决策 ADR、技术选型、数据流）
│   └── INDEX.md
├── ref/              # 参考资料（外部文档、调研、规范引用）
│   └── INDEX.md
└── assets/           # 截图等附件（被 log/design 引用，日期命名；无 INDEX）
```

> 分类按项目实际增删。小任务可在一个文件中分设 Spec、Plan、变更记录；复杂度增长后再拆分。保留仓库已有路径，不强制迁移到 `doc/`。非开发项目（skill 仓库、内容）的分类不同——用各自的领域分类，但**索引 + 分片 + 按需读原则不变**。

---

## 二、命名规则：内容文件都带日期

所有**内容文件**用 `YYYY-MM-DD-{标识}.md`——日期在前，按时间自然排序，看文件名就知道何时写的。

| 分类 | 命名 | 示例 |
|------|------|------|
| log/ | `{YYYY-MM-DD}.md`（日期即标识） | `log/2026-08-12.md` |
| plan/ | `{YYYY-MM-DD}-{阶段}-{主题}.md` | `plan/2026-08-12-m1-auth.md` |
| spec/ | `{YYYY-MM-DD}-{功能域}.md` | `spec/2026-08-12-auth.md` |
| design/ | `{YYYY-MM-DD}-{决策主题}.md`（ADR 风格） | `design/2026-08-12-use-postgres.md` |
| ref/ | `{YYYY-MM-DD}-{来源/主题}.md` | `ref/2026-08-12-stripe-api.md` |
| assets/ | `{YYYY-MM-DD}-{标识}.{ext}` | `assets/2026-08-12-auth-error.png` |

**规则**：
- 日期 = 创建日期，文件名稳定不改；重大重写新建带新日期的文件，旧的归档
- **`INDEX.md` 不加日期**——它是活索引，持续更新，永远只有一份当前的
- 一天多个同类文件用标识区分（如同日两个 spec：`...-auth.md`、`...-payment.md`）
- `assets/` 无 INDEX——LLM 不读它，只被 log/design 等条目按相对路径引用

## 三、规格轨：spec/

**放什么**：需求定义、产品规格、验收标准、接口契约。相对稳定，变更需评审。

**调研先行**：写 spec 前先调研开源/已有方案——同类产品用什么、有哪些可复用库/成熟项目。调研记 `ref/`（每个候选：是什么、优劣、能否复用），spec 里记录关键能力的"**自研 vs 复用**"选型——只有核心差异化能力才自研，防止早期什么都从零造。

**spec 文件骨架**（借鉴 Spec Kit：机器可判的验收标准是关键，每个分片按此结构）：

```markdown
# {功能域} 规格

## Summary
{1-2 句终端用户视角：这个功能做什么}

## 验收标准
- [ ] 作为{角色}，我要{动作}，以便{价值}——Given {前置} When {操作} Then {结果}

## 功能需求
- {系统该做什么}

## 非功能需求
- 性能：{如列表 API < 500ms} · 安全：{如输入全量校验} · 可扩展：{如水平扩容}

## 边界情况
- {异常场景、错误条件、边界行为——字段为空/超限/含特殊字符时怎样}

## 选型记录
- {能力}：自研 / 复用 {方案}（理由，见 ref/；已有结论可直接引用）

## 架构与组件影响（涉及结构或共享能力时填写）
- 复用 / 扩展 / 新建：{现有模块或组件路径、理由}
- 职责、依赖方向、状态归属：{业务逻辑与数据访问边界}
- 接口兼容、迁移与受影响调用方：{处理方式}

## UI 与交互约束（涉及界面时填写）
- 设计系统、Token、参考页面：{有效来源路径，不复制整套定义}
- 加载 / 空 / 错误 / 成功 / 禁用状态：{适用状态及用户可见行为}
- 响应式、键盘操作与焦点行为：{适用要求}

## 验收与回归
- {需求 ID} → {用户操作与预期结果} → {验证命令或人工检查方式}
- 受影响页面、组件、接口：{回归范围及证据要求}

## 有效性
- 状态：草案 / 有效 / 已替代 / 已废弃
- 依据：{用户决策或已授权范围}；替代关系：{如适用}

```

**分片**：按功能域或模块拆，一个 spec 一个文件，命名 `spec/{YYYY-MM-DD}-{功能域}.md`。如 `spec/2026-08-12-auth.md`、`spec/2026-08-20-payment.md`。

**INDEX.md**：
```markdown
# spec/ 索引

| 功能域 | 状态 | 一句话定义 | 文件 |
|--------|------|-----------|------|
| 认证 | 稳定 | OAuth2 + 本地会话 | [2026-08-12-auth.md](spec/2026-08-12-auth.md) |
| 支付 | 草案 | 待定渠道，先记需求 | [2026-08-20-payment.md](spec/2026-08-20-payment.md) |
```

**读**：开工前只读 `spec/INDEX.md`；要做某模块才读对应 spec。

**写**：新增/大改规格 → 新建或改 spec 文件 → 更新 `spec/INDEX.md`。

## 四、计划轨：plan/

**放什么**：实施计划——做什么、顺序、每步成功标准。面向未来，按迭代/里程碑/功能域组织（不按日期）。

**分片**：`plan/{YYYY-MM-DD}-{阶段}-{主题}.md`。如 `plan/2026-08-12-m1-auth.md`、`plan/2026-09-01-refactor-db.md`。

**INDEX.md**：
```markdown
# plan/ 索引

| 阶段 | 状态 | 目标 | 文件 |
|------|------|------|------|
| M1 认证 | 进行中 | 登录/注册/会话 | [2026-08-12-m1-auth.md](plan/2026-08-12-m1-auth.md) |
| M2 支付 | 已变更 | 被 09-20 v2 替代，渠道改 Stripe | [2026-09-08-m2-payment.md](plan/2026-09-08-m2-payment.md) |
| M2 支付 v2 | 未开始 | 接入 Stripe | [2026-09-20-m2-payment-stripe.md](plan/2026-09-20-m2-payment-stripe.md) |
```

**任务清单**：每个计划分片末尾附可勾选任务——`- [ ] {任务}（验证：{命令/方式}）`，完成即勾选并记当天 log。计划答"怎么做"，任务答"下一步具体做什么"，一层层落到可执行（借鉴 Spec Kit 的 plan → tasks 分层）。

**读**：开工前读 `plan/INDEX.md` 看当前阶段；只读当前阶段的计划分片。

**写**：开工前更新当前阶段计划；阶段推进或方向变了，更新 `plan/INDEX.md` 状态，必要时新建计划分片。

**变更纪律**：所有新建、修改、替代计划均按以下协议执行。

1. **定位有效依据**：读取相关 Spec、设计决策及计划索引。同一范围只能有一套有效约定；不同范围可并行。Plan 不得擅自改写 Spec，Log 中影响现行行为的决定必须同步回有效文档。按明确授权和替代关系判断，不按文件日期猜优先级。
2. **检查影响**：列出受影响需求、任务、组件、接口、测试、调用方及已完成实现；检查重叠、矛盾和下游依赖。重叠时合并或划清范围，冲突不能静默折中。
3. **按授权推进**：仅改实现方式或顺序且不改变已授权范围、验收和约束，更新计划后直接继续。用户明确要求改变行为，先同步 Spec 再改计划，不重复确认。尚未决定的范围、验收或兼容性取舍，只暂停受影响部分并提出具体决策问题；独立工作继续。
4. **局部替代**：任务用稳定 ID。局部变化只将相关任务标为已替代并指向替代任务；其余任务保留。整份替代才将旧计划标为已变更，旧文件保留，新旧文件及索引互相链接并写明原因。
5. **复核已有工作**：依赖旧方案的任务（含已完成任务）标为待复核；逐项决定已有代码保留、修改、迁移或移除，更新验证范围。旧测试通过不等于符合新要求。
6. **同步后实施**：更新有效 Spec、必要的设计决策、计划及索引，Log 记录原因、依据、影响、替代关系和未决项，再执行受影响实现。长期规则未变化时不改 AGENTS.md。
7. **恢复与验收**：开始或恢复时确认有效依据和依赖状态，将可执行的未开始任务转为进行中；待复核任务先完成影响分析并补齐工作再执行。已替代、已废弃和受阻任务不得继续；完成须有针对当前验收的证据。

计划状态：`未开始 / 进行中 / 受阻 / 已完成 / 已变更（指向替代计划）/ 已废弃`。
任务状态：`未开始 / 进行中 / 待复核 / 受阻 / 已完成 / 已替代 / 已废弃`。

任务最小记录：`ID | 需求依据 | 依赖任务 | 状态 | 验证方式/结果 | 替代关系（如有）`。记录在当前计划内，不额外建任务系统。

**检查点**：阶段结束或工作中断时，在当前计划记录有效 Spec/设计指针、已完成及待复核任务、阻塞项、下一条可执行任务；Log 留验证证据。恢复时核对文件和实际实现，不凭聊天记忆继续。

## 五、日志轨：log/

**放什么**：执行记录——每次工作的目标、变更、决策、验证、缺口。追加式，不流水账。

**分片**：按日期拆，`log/{YYYY-MM-DD}.md`。一天多次工作用二级标题分隔。

**INDEX.md（倒序，最新在上）**：
```markdown
# log/ 索引（最新在上）

| 日期 | 类型 | 一句话结论 | 文件 |
|------|------|-----------|------|
| 2026-08-12 | 决策 | 选 PostgreSQL 不选 MySQL，成本与生态 | [2026-08-12.md](log/2026-08-12.md) |
| 2026-08-11 | 实现 | 完成登录 API，测试通过 | [2026-08-11.md](log/2026-08-11.md) |
```

**读**：开工前读 `log/INDEX.md` 看最近结论；回溯某决策才读对应日期分片。

**写**：收工后追加 `log/{YYYY-MM-DD}.md`，并在 `log/INDEX.md` **顶部**加一行（日期·类型·一句话结论·指针）。

**截图留存**：log 记录**关键判断或失误修正**、且过程有截图（错误现场、复现步骤、验证结果、前后对比）时，截图一并存档——文字描述会丢细节，回溯时一张现场截图比几行文字可靠。截图复制/移动到 `doc/assets/`（命名 `{YYYY-MM-DD}-{标识}.png`，与 log 同日期前缀），log 条目用相对路径引用：`![{说明}](../assets/2026-08-12-auth-error.png)`。没有截图不强求补拍；与判断/修正无关的过程截图不存——宁缺毋滥。

## 六、统一执行管理：spec → plan → log 闭环

三轨不是独立文件夹，是一条闭环。每次工作串起来：

```
读 spec/INDEX（要做什么）
   ↓
读 plan/INDEX + 当前计划分片（怎么做、到哪步；**核对有效状态与依赖；可执行的未开始任务转为进行中，失效任务不执行**）
   ↓
读 log/INDEX 顶部（最近做了什么、有什么决策/缺口）
   ↓ 【开工】
实现 + 用「构建与测试」命令验证
   ↓ 【收工】
追加 log/{日期}.md（目标·变更·决策·验证·缺口）
   + 关键判断/失误修正有截图 → 存 doc/assets/ 并在 log 条目里引用
   + log/INDEX 顶部加一行
   + spec/plan 变了 → 更新对应 INDEX 与分片
```

**铁律**：INDEX 只放指针和一句话结论，细节进分片。INDEX 永远小（几十行），这是渐进式读取能成立的前提。

**评审门**：先检查现有授权。已授权的需求与常规实施调整，完成文档同步即可推进；只有未决的产品范围、验收或兼容性取舍需要用户决策。禁止机械地在 Spec、Plan、Tasks 每层重复请求确认。

## 七、渐进式读取协议（LLM 通用）

适用于 **doc/ 下所有文件夹**，不只 plan/log：

1. **先读 INDEX，不全量读分片**——进任何文件夹先读它的 `INDEX.md`
2. **按指针读 1-2 个分片**——INDEX 指向哪个需要细看，才读那个
3. **不读历史全部**——除非回溯某个具体决策（INDEX 会指过去）
4. **写完更新 INDEX**——新建/改分片，同步更新所属 INDEX 的指针和结论

**判断"要读哪些"**：看 INDEX 的"状态"和"一句话结论"列——只读与当前任务相关的、或最近变更的。

## 八、文档分类总表

| 分类 | 放什么 | 稳定性 | 默认有无 |
|------|--------|--------|---------|
| spec/ | 需求、产品规格、验收标准、契约 | 稳定（变更需评审） | 有规格定义就有 |
| plan/ | 实施计划、迭代计划 | 中（按阶段更新） | 推荐 |
| log/ | 执行日志、决策记录 | 追加（只增不改） | 必需 |
| design/ | 架构决策（ADR）、技术选型、数据流 | 稳定 | 有架构决策就有 |
| ref/ | 选型调研（开源/已有方案对比与结论）、外部资料、规范引用 | 稳定（候选追加） | 做过调研就有 |
| assets/ | 截图等附件（被 log/design 等引用） | 追加（只增不改） | log 有关键判断/失误修正的截图就有 |

**非开发项目的分类不同**：skill 仓库可能是 `skills/`（每个 skill 自带文档）+ `log/`；内容项目可能是 `topics/` + `drafts/` + `log/`。分类按业务定，**索引 + 分片 + 按需读原则不变**。

## 九、doc/INDEX.md 示例

项目文档的总入口，列出所有分类文件夹：

```markdown
# 项目文档索引

LLM 进来先读本文件，按需读各分类的 INDEX，再读具体分片。

## 文档分类

| 分类 | 用途 | 入口 |
|------|------|------|
| spec/ | 需求与规格 | [spec/INDEX.md](spec/INDEX.md) |
| plan/ | 实施计划 | [plan/INDEX.md](plan/INDEX.md) |
| log/ | 执行日志（最新在上） | [log/INDEX.md](log/INDEX.md) |
| design/ | 架构决策 | [design/INDEX.md](design/INDEX.md) |

## 当前焦点

- 进行中：M1 认证（见 plan/2026-08-12-m1-auth.md）
- 最近决策：选 PostgreSQL（见 log/2026-08-12.md）
```

"当前焦点"两行让 LLM 一进 doc/ 就知道现在在干嘛、最近定了什么，不用翻 INDEX。

## 十、长期规则与有效来源

- AGENTS.md：长期执行约束、授权边界、验证入口；不写当前任务进度。
- Spec：当前产品行为、范围、验收；Design：组件边界、设计系统和重要决策理由。
- Plan：当前实施步骤、依赖和状态；Log：历史原因与验证证据，不作为隐式新规格。
- 详细定义只维护一份，其他文档引用；批准迁移时明确目标、适用范围、过渡兼容和完成条件，不把目标描述成已实现。
