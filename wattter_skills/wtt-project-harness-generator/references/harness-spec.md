## Harness 架构

```
项目根目录/
├── CLAUDE.md                  # 核心项目指令（< 200 行）
├── CLAUDE.local.md            # 个人偏好（.gitignore）
├── AGENTS.md                  # 跨工具通用指令
├── .claude/
│   ├── settings.json          # 共享项目设置
│   ├── settings.local.json    # 个人设置（.gitignore）
│   └── rules/                 # 模块化路径范围规则
│       ├── code-style.md      # 无条件规则
│       └── api/
│           └── endpoints.md   # 路径范围规则
└── .mcp.json                  # 项目级 MCP 服务器
```

### 组件强制性

| 组件 | 强制性 | 说明 |
|------|--------|------|
| CLAUDE.md | 指导性 | 上下文塑造行为，不保证 100% 遵守 |
| .claude/rules/ | 指导性 | 按需加载，节省上下文 |
| settings.json permissions | 强制性 | deny 优先于 allow |
| settings.json hooks | 强制性 | 确定性执行，不管 LLM 决定什么 |

## 组件选用决策

| 场景 | 使用 |
|------|------|
| Claude 两次犯同一约定错误 | CLAUDE.md 规则 |
| 规则仅适用部分文件 | .claude/rules/ + paths frontmatter |
| 每次都必须执行某操作 | Hook（非提示指令） |
| 重复输入相同提示 | Skill |
| 限制/允许特定命令 | settings.json permissions |

**关键**：必须保留的规则用 hook，不用提示指令。

## 新项目 vs 已有项目

扫描先判断项目阶段，决定走哪条分支——这决定后续是对话主导还是扫描主导。

### 判断标准

| 信号 | 判断 |
|------|------|
| 空文件夹 / 只有 `.git` / 只有 README | 新项目 |
| 只有 `package.json`/`pyproject.toml` 等清单，无 `src/`/`app/` 源码 | 新项目（刚 init） |
| 有源码文件、有目录结构 | 已有项目 |
| 有现成 CLAUDE.md/AGENTS.md | 已有项目（要决定保留还是重写） |

拿不准就问一句："这是新项目还是要优化已有项目？"

### 两种模式对比

| 维度 | 已有项目 | 新项目 |
|------|---------|--------|
| 信息来源 | 扫描代码（读码推断） | 对话定义（问用户） |
| 规则性质 | 描述性——"现状是什么" | 规定性——"该怎么做" |
| 立场来源 | 从既有代码风格/架构提炼 | 用户定义目标 + 选型，按 [立场定调](#立场定调按项目领域) 定 |
| 命令/结构 | 从 package.json/Makefile 提取 | 用户选型后填入（先用约定值） |
| 额外动作 | 保留既有 doc 结构、迁移旧 AI 配置 | 搭 doc/ 骨架 + 建议初始目录结构 |

**已有项目**：规则要忠实反映现状，发现代码与约定矛盾时选一个贯彻，别把"理想"写成"现状"。

**新项目**：规则是给项目定的规矩，从第一天就立好。用户没决定的（如测试框架、目录结构）给合理默认值，标出来让用户确认，不留空。**调研先行**：产品构思阶段（写第一份 spec 前）先调研开源/同类方案，能复用不自研，调研记 `doc/ref/`——从源头控制"早期什么都从零造"。

### 新项目脚手架

新项目除了生成 CLAUDE.md/AGENTS.md，顺手搭文档骨架，让项目起步即有文档管理（规范见 [doc-management.md](doc-management.md)）：

```
项目根/
├── CLAUDE.md / AGENTS.md    # 本 skill 生成
└── doc/
    ├── INDEX.md             # 总索引（含"当前焦点"两行）
    ├── spec/INDEX.md        # 规格（先空，定义需求时填）
    ├── plan/INDEX.md        # 计划（第一个迭代从这里开始）
    └── log/INDEX.md         # 日志（第一次工作后开始记）
```

每个 INDEX 初始只放表头 + 一句"项目刚启动"，等有内容再填。产品构思阶段做过开源调研就建 `ref/`；design/ 按需再加。

> 新项目第一天的 `log/` 就记一条："初始化项目，技术栈 X，首个目标 Y"——让下一个进来的 agent（或下一次会话）一读 log/INDEX 就知道项目从哪开始。

## 组件化推断

| 项目类型 | 组件化模式 |
|----------|-----------|
| React 前端 | 函数组件 + Hooks，按功能域分目录 |
| Vue 前端 | SFC + Composables，按功能域分目录 |
| Angular | Module/Component/Service 三层 |
| Next.js 全栈 | App Router 路由组 + Server Components |
| Django | App 分模块，MTV 模式 |
| Spring Boot | Controller/Service/Repository 三层 |
| Go | Handler/Service/Repository + 接口抽象 |
| Monorepo | Packages 分包，apps 消费 packages |

### 组件抽离时机

以下阈值只触发评审，不直接决定拆分。依据职责混杂、状态耦合、独立变化和真实复用需求划分边界，不为了行数或参数数量制造新抽象。

**前端信号**：

| 信号 | 动作 |
|------|------|
| 同一段 JSX/模板重复 ≥ 2 次 | 确认语义与变化方向一致后决定复用 |
| 组件内条件渲染嵌套 ≥ 3 层（三元 / `&&` 嵌套） | 评审状态模型与职责边界 |
| Props > 5 个 | 评审接口内聚性，不用配置对象隐藏复杂度 |
| 同一状态/副作用逻辑在 ≥ 2 个组件出现 | 生命周期与语义一致时抽 Hook / Composable |
| 单组件 > 300 行 | 存在独立职责或变化边界时拆分 |

**后端信号**：

| 信号 | 动作 |
|------|------|
| 同一业务校验在 ≥ 2 个 handler 出现 | 下沉到 service 或 middleware |
| 同一数据访问模式重复 | 抽 repository / data access 层 |
| 函数 > 80 行 或 参数 > 5 | 评审职责与参数内聚性，不机械拆分或打包 |
| 一个类/模块承担 > 1 个变更原因 | 按职责拆分 |
| 跨模块共享的领域逻辑 | 抽到 domain/shared 层，不放进 controller |

## 立场定调（按项目领域）

生成的 AGENTS.md/CLAUDE.md 要有一条**项目业务的立场**——不是规则堆，是对"这个项目的活儿该怎么干"的表态。立场按领域定调，带可验证约束，不写口号：

| 项目领域 | 立场定调 |
|---------|---------|
| 软件开发 | 组件化/分层：前端=先定边界、组合吸收变化；后端=分层单向依赖；CLI=组装与逻辑分离 |
| Skill / 知识仓库 | 改优于写（解构高手 skill → 适配，不从零造）；四处同步；执行文件只写当前规则 |
| 内容创作 | 价值优先、去营销化（避免被判广告）；平台适配；可空参数问用户不跳过 |
| 课程 / 教育 | 教学法先行（如八步曲）；学员视角；以学员能学会为成功标准 |

**开发项目的立场进组件化节（见上）；非开发项目用「核心立场」节替代组件化节，谈本领域业务态度。** 示例见 [agents-md-templates.md](agents-md-templates.md) 的 Skill 仓库示例。

## UI/UX 规范推断

### D-S-T-E 体验四步曲

所有项目的 UX 规范按 D-S-T-E 四步闭环生成：

```
诊断（盲测）→ 简化（3-5铁律）→ 翻译（说人话）→ 升温（微交互+AI）
     ↑                                                    ↓
     └────────────── 形成闭环，持续迭代 ──────────────────┘
```

**口诀**："盲三点，简三五，翻译说人话，升温微交AI"

- 盲三（点）：盲测发现 3 秒停顿点
- 简三五（步）：3 步点击，5 步操作
- 说人话：翻译成用户语言
- 微交 AI：微交互 + AI 升温

### 按项目类型适配 D-S-T-E

**Web 应用**：

| D-S-T-E | 生成内容 |
|---------|---------|
| D 诊断 | 盲测法则 + 用户情绪地图 + 3 秒停顿检测 |
| S 简化 | 3-5 铁律 + 奥卡姆剃刀 + 预判需求 + 预填写 |
| T 翻译 | 黑话扫雷 + 占位符指引 + 按钮行动化 + 错误提示可操作 |
| E 升温 | 微交互动效 + 安抚机制 + 无障碍 + 确定性预期 |

**API 后端**：

| D-S-T-E | 生成内容 |
|---------|---------|
| D 诊断 | API 响应时间监控 + 错误率热点 |
| S 简化 | 最少必须参数 + 合理默认值 + 批量操作 |
| T 翻译 | 可操作错误信息（code + message + suggestion）|
| E 升温 | 长操作进度反馈 + 健康检查摘要 + 可交互文档 |

**CLI/库**：

| D-S-T-E | 生成内容 |
|---------|---------|
| D 诊断 | 命令失败率监控 |
| S 简化 | 最少 flag + short alias + 交互式引导 |
| T 翻译 | 人类可读错误 + 修复建议 |
| E 升温 | 进度条 + 彩色输出 + quiet/verbose 模式 |

**数据/ML**：

| D-S-T-E | 生成内容 |
|---------|---------|
| D 诊断 | 数据异常检出 + 输入 schema 校验 |
| S 简化 | 自动推断 schema + 合理默认参数 |
| T 翻译 | 图表标题/轴标签/图例 + 异常给出具体行号字段 |
| E 升温 | 训练 metrics 可视化 + 进度预估 |

### D-S-T-E 关键方法速查

**诊断方法**：
- 盲测法则：找非专业用户测试，卡住就是产品不合格
- 3 秒停顿：用户操作停顿超过 3 秒的步骤，必须标注原因
- 跳出率热点：用户需要跳出产品找帮助的步骤，视为缺陷
- 恐惧点：用户"怕填错"的犹豫，需要安抚或简化

**简化方法**：
- 3-5 铁律：核心需求 ≤ 3 次点击，完整流程 ≤ 5 步
- 奥卡姆剃刀：不是 100% 必须的输入框就删掉
- 预判需求：用户复制卡号→弹转账提示；连续输错→提示找回密码
- 预填写：能自动填充的字段绝不手动输入

**翻译方法**：
- 黑话扫雷：专业术语→用户语言（借记卡→储蓄卡，签约→开通）
- 占位符指引：别只写"请输入"→写"1000 元起购，1 元递增"
- 按钮行动化：别只写"确定"→写"立即拿钱"
- 错误可操作：✗"代码 9908" → ✓"余额不足，可用余额 xx 元，先转这么多？"

**升温方法**：
- 微交互：成功动效、成就反馈
- 安抚机制：加载 > 3 秒别只转圈圈，给有趣动画或有用信息
- 确定性预期：等待时告诉用户"还需要约 30 秒"
- AI 辅助：用 AI 工具快速生成整改原型

### 按团队规模

| 规模 | 严格度 | 覆盖范围 |
|------|--------|---------|
| 1人 | 宽松 | 命名 + 测试 |
| 2-5人 | 中等 | 命名 + 组件化 + UI/UX + 测试 |
| 5-20人 | 严格 | 全部章节 + 路径规则 |
| 20+人 | 最严格 | 全部 + hooks + CI gates |

## 对话引导问题

### 必问（扫描推断不了时）

1. **项目类型**：Web 应用 / API 服务 / CLI 工具 / 库 / 数据/ML / 全栈 / Skill 或知识仓库 / 内容创作 / 课程 / 其他
2. **团队规模**：1人 / 2-5人 / 5-20人 / 20+人
3. **输出范围**：CLAUDE.md / AGENTS.md / .claude/rules/ / settings.json

### 按需追问

4. **核心领域对象**：项目有哪些关键概念？（如 Goal·Task·Approval·Artifact）
5. **特有规则**：有什么是 Agent 容易犯错、必须遵守的硬规则？
6. **设计系统**：项目有设计系统或风格指南吗？具体 token 是什么？
7. **复用调研**：是否有参考项目/开源方案可优先复用？产品构思的调研做过吗？（没有则先调研再写 spec，记 doc/ref/）
8. **已有配置**：是否已有 CLAUDE.md 或 AGENTS.md？保留还是重写？
9. **部署方式**：Docker / K8s / Serverless / 传统？
10. **测试要求**：覆盖率目标？CI 位置？
11. **文档管理**：项目是否用 doc 分类（spec/plan/log）+ INDEX 分片管理？路径是？（未检测到则建议建立，见 [doc-management.md](doc-management.md)）

## 设计约束落地

AGENTS.md 维护长期的组件边界、依赖方向、Token 来源与共享修改回归规则；功能 Spec 记录本次复用/扩展/新建、状态归属、兼容迁移、受影响调用方和 UI 验收。Design 保存详细设计系统与重要架构决策，其他文档引用。规则片段见 [AGENTS.md 模板](agents-md-templates.md)，Spec 字段见 [文档管理](doc-management.md)。

## Skill 项目的版本化测试

单个 Skill 与多 Skill 仓库都适用 [版本化对照测试协议](skill-evaluation.md)。扫描已有测试目录、固定输入、生成步骤、评审标准和历史产物，优先复用；缺失时落地测试集骨架。AGENTS.md 只承载每次修改必须对照验证和追加归档的长期要求；按版本标记的样例、快照与报告放 tests/evals/ 等实际入口，不加载全部历史。测试新输出是 observed，评审后才是 reference，失败补成 regression。
