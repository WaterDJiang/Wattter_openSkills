# 知识时效机制 — 让每张卡片带时间先后，可答"哪个最新、哪个被推翻"

本文件定义 wiki 的时间维度设计。没有时效的 wiki 有一个隐蔽缺陷：新旧知识并存时**平级展示**，检索无法分辨"这是最新结论"还是"这是已被深化的旧版本"。本机制让知识落盘时就带上时间先后，编译时做新旧碰撞判定，检索时输出知识时间与状态。

## 1. 三个时间字段的分工

| 字段 | 含义 | 变化时机 | 用途 |
|:---|:---|:---|:---|
| `knowledge_date` | **知识发生时间**——来源资料的时间，不是编译时间 | 永不变化（内容地位变了也不改） | 排序、新旧判定、时效回答 |
| `created` / `date` | 卡片创建时间（note 用 `date`） | 建卡时写一次 | 个人笔记时间线 |
| `last_compiled` | 最后编辑时间 | 每次合并/追加都更新 | 追溯"什么时候动过这张卡" |

**核心区分**：`last_compiled` 只记"编辑过"，分不清「内容小修」和「知识地位变化」（被深化/被推翻）。`knowledge_date` 承担后者——它是知识的"出生日期"，一旦回填永不再改。

## 2. 字段约定

```yaml
# 所有知识卡片（kp/case/model/concept）必填
knowledge_date: 2026-07-27        # YYYY-MM-DD，知识发生时间

# 可选，回填脚本/编译器在"近似推断"时才写（精确推断不写，保持干净）
knowledge_date_basis: approximate  # exact=来源文件名日期前缀 / approximate=兜底推断

# 可选，仅当本卡被新知识取代/深化时由编译器填（不擅自标，必须用户确认）
superseded_by: "[[新模型名]]"      # 值为目标卡片文件名或相对路径
```

**字段归属**：

| 卡片类型 | knowledge_date | 说明 |
|:---|:---|:---|
| kp / case / model / concept | **必填** | 知识卡片，时效是检索必需维度 |
| note | 不加（已有 `date` 承担） | 单点真相，不重复加字段 |
| material | 可选 | 素材时效性弱，有就填 |

## 3. knowledge_date 推断规则（编译时 + 回填时共用）

按优先级取**第一个命中**：

| 优先级 | 来源 | basis |
|:---|:---|:---|
| 1 | `source_files` 中 raw 文件名的日期前缀（`YYYYMMDD_` / `YYYY-MM-DD`），取**最早** | `exact`（不写 basis 字段） |
| 2 | raw 文件实际存在 → 文件修改时间 | `approximate` |
| 3 | frontmatter 已有 `created` / `last_compiled` / `date` | `approximate` |
| 4 | 都没有 → 编译日期兜底 | `approximate` |

> 用"最早"而非"最新"：一张卡的知识地位由它首次出现的资料决定；后续补充资料只改 `last_compiled`。

## 4. 编译时：新旧碰撞判定

触发条件：本次输入资料产出的知识，与 wiki 中**已有卡片同体系**（同一主题/同一方法谱系，不只是同名——名字完全不同但语义演进的也要靠语义判定抓出来）。

判定流程（在合并模式之前执行）：

```
识别同体系对 → LLM 读两侧内容语义判定 → 四分类：
├── 互补（新资料深化/细化旧知识，不推翻）
│     → 走合并模式追加；不标 superseded_by
├── 取代（新知识推翻/覆盖旧知识的地位）
│     → 旧卡 frontmatter 标 superseded_by: "[[新卡]]"
│     → 新卡加「演进史」段，写清差异与取代理由，回链旧卡
│     → 旧卡保留展示，不删除不改写正文
├── 并存（同主题但适用场景/角度不同）
│     → 不标取代；两卡互写关联 + 边界对比（各自适用边界）
└── 拿不准 → 列成候选表请用户确认，本次不标
```

**铁律：不擅自标 superseded_by。** 字面相似 ≠ 知识演进（可能是跨域类比、同主题不同侧面），取代判定必须语义确认 + 用户确认。

### 「演进史」段模板（新卡 body 末尾，可选段）

```markdown
## 演进史

| 时间 | 卡片 | 关系 |
|:---|:---|:---|
| 2026-06-14 | [[人本位vs-AI本位Agent范式]] | 本模型深化了其中 L2→L3 的分界点判断 |
```

## 5. 检索时：时效呈现契约

任何涉及知识卡片清单的输出（回答、对比、盘点），涉及同体系多张卡时必须带时间与状态：

| 规则 | 说明 |
|:---|:---|
| 输出加「知识时间」「状态」两列 | 时间用 `knowledge_date`，不用 `last_compiled` |
| 同体系归组展示 | 同一谱系的卡片放一起，不散落在列表各处 |
| 最新标 ✅ 优先使用 | ✅ 2026-07-27　Prompt到Agent范式转移 |
| 旧版标注但保留展示 | ⚠️ 已被 [[新卡]] 深化　2026-06-14　旧模型 |
| 用户问"X 还成立吗/有没有被推翻" | `rg 'superseded_by'` + 读新卡演进史，给出演进链 |

**排序规则**：同体系内按 `knowledge_date` 升序（旧→新，演进链可读）；跨体系按 `knowledge_date` 倒序（新→旧，最新优先）。

## 6. Lint：时效检查（L17/L18）

| 检查 | 档位 | 内容 |
|:---|:---|:---|
| **L17 知识时效字段** | 轻量 | knowledge_date 缺失（note 卡查 `date`）/ 格式非法 / 未来日期 / basis 取值非法 |
| **L18 新旧体系健康** | 深度 | ① superseded_by 链：死链（目标不存在）+ 回链缺失（新卡未写回旧卡）② 同体系候选扫描：同领域内模型名共享 ≥3 字中文子串（剔除通用词、纯 ASCII 碎片）、时间有先后、未标取代关系 → 列为候选 **info**，只提示不标 |

**已知局限（必须写进报告）**：字面候选扫描会**漏报**名字无共享词的语义演进对（如「四层级 → 沉淀积累」），也会偶发噪音。候选清单只是辅助——真正的取代判定靠编译时碰撞判定（LLM 语义）+ 用户确认。

## 7. 存量回填（backfill_knowledge_date.py）

已有 wiki 首次上时效机制时，用 `scripts/backfill_knowledge_date.py` 批量回填：

```bash
python3 scripts/backfill_knowledge_date.py {目标目录} --dry-run   # 先看计划
python3 scripts/backfill_knowledge_date.py {目标目录}             # 正式执行（幂等可重跑）
```

**流程铁律**（来自实战踩坑）：`--dry-run` 看清单 → **抽查 2-3 个文件的实际 diff** → 正式执行 → 再抽查确认无格式问题。批量改文件的脚本跳过抽查=赌博。

**输出**：精确推断 / 近似推断（清单单独列出备查）/ 无法推断 三类分开报告。近似推断的卡片会写入 `knowledge_date_basis: approximate`，便于事后甄别。

**迁移到其他 wiki 的适配点**：
1. 字段名对齐——目标库 schema 若用 `concept` 而非 `model` 等，改脚本的 `REQUIRED_FIELDS` 与字段插入位置
2. 日期前缀——目标库 raw 文件名无 `YYYYMMDD_` 前缀时，回填会全走近似兜底；先决定是否接受，或手工补关键卡
3. 目标库若无 `[[双向关联]]` 机制，先只回填 knowledge_date + 上检索排序（收益最大、零风险），碰撞判定和 L18 链检查等关联机制就绪后再上

## 8. 实战踩坑记录

| 坑 | 教训 |
|:---|:---|
| 批量插行脚本一个字符传错，97 个文件插出多余空行，二次批量修正 | 批量改文件必须 dry-run + 抽查实际 diff 再全量执行 |
| 同体系扫描用纯字面 4-gram，把 Agent/AI 前缀模型全部配对（39 对噪音） | 只保留含中文的子串（纯 ASCII 碎片多是主题泛词切片），且剔除通用词后配对数降到个位数 |
| 字面启发式漏报：名字无共享词但语义演进的知识对 | 候选清单只是辅助，取代判定靠编译时 LLM 语义判定 + 用户确认 |
