# Context Judging — 主语境判定细则

> **何时用**：在 Build 模式 B2、Compile 模式第零步之前、用户首次使用本 skill 时——判定这个 wiki 服务于哪种主语境。
>
> **核心问题**：这个 wiki 是给谁用的、用来做什么、产出物的形态是什么？

---

## 四种主语境一览

| 主语境 | 一句话 | 主产物 | 主索引段 |
|:---|:---|:---|:---|
| **课程** | 教别人一套结构化知识 | kp（知识点） + module（模块） | 课程清单 / 模块索引 / 三线 |
| **知识库** | 让团队/后人能查到一套已沉淀的知识 | concept / model / case | 主题索引 / 概念索引 / 共享素材 |
| **个人笔记** | 自己将来能回看、思考、串联的记录 | note（通用笔记） | 时间线 / 主题分组 / 项目分组 |
| **综合** | 多种混用 | 全部并存 | 多维索引 |

---

## 判定方法

### 第 1 问：谁会用这个 wiki？

| 答案 | 主语境 |
|:---|:---|
| 主要给学员/读者用，按讲次/模块学习 | **课程** |
| 主要给团队成员/新人查阅，按主题查 | **知识库** |
| 主要给"未来的自己"或同侪看，按时间/项目回看 | **个人笔记** |
| 多种用户都有 | **综合** |

### 第 2 问：原始资料的形态是什么？

| 资料形态 | 主语境倾向 |
|:---|:---|
| 课纲 / 讲义 / 教学视频转写 | 课程 |
| 产品文档 / 技术手册 / 方法论文档 / 案例集 | 知识库 |
| 读书摘录 / 会议记录 / 聊天记录 / 个人日记 / 收藏 | 个人笔记 |
| 混合 | 综合 |

### 第 3 问：检索时的入口是什么？

| 入口 | 主语境倾向 |
|:---|:---|
| "这门课第几讲讲了什么" | 课程 |
| "MECE 原则在我们的知识库里怎么定义的" | 知识库 |
| "我去年关于 X 的笔记在哪" | 个人笔记 |

> 三个问题答案一致 → 主语境明确。三选二即可。

---

## 主语境的特征对照

### 课程语境

**典型场景**：培训课件、课程开发、教学材料、内部讲师手册、读书会输出

**主目录**：`wiki/kps/` + 模块子目录

**萃取骨架**：模块 → 知识点 → 四点三线（焦点/卖点/特点/笑点）

**索引侧重**：按模块、按领域、按讲次

**强约束**：
- 知识点必须"独立可讲授"
- 必须有"卖点"（为什么值得讲）
- 模块间不能太跳（学习者跟得上）
- source_marking 严格：[已提取] vs [AI补全] 必须分清

**示例 wiki**：
- 选题方法论（6 个模块、35 个知识点）
- AI 产品经理培训课（4 个模块、28 个知识点）
- 银行信贷审批内部培训（5 个模块、40 个知识点）

### 知识库语境

**典型场景**：团队 wiki、产品文档库、方法论库、最佳实践库、案例库

**主目录**：`wiki/concepts/` + `wiki/models/` + `wiki/cases/`

**萃取骨架**：主题 → 概念 / 模型 / 案例 + 共享素材

**索引侧重**：按主题、按领域、按类型、按更新时间

**强约束**：
- 概念/模型/案例必须"可被检索"
- 共享素材（`materials/`）是核心
- 跨主题关联（`appears_in`）必须双向写回
- source_marking 严格但允许"AI 补全定义"——知识库常需要把零散文档合成完整定义

**示例 wiki**：
- 设计系统知识库（50 个组件、20 个模式、30 个案例）
- 投融资方法论库（15 个模型、80 个案例、200 个素材）
- 团队 OKR 实践库（10 个流程、25 个工具、40 个反思 note）

### 个人笔记语境

**典型场景**：个人 PKM、读书笔记、会议记录、日常思考、灵感、观察

**主目录**：`wiki/notes/`

**萃取骨架**：来源 → 笔记 / 摘录 / 思考 + 时间线

**索引侧重**：按时间线、按主题、按项目、按笔记类型

**强约束**：
- 不强求结构（笔记是自由的）
- 必须有 `date` 字段（个人笔记的核心是时间序列）
- 不强制双向关联（个人笔记关联是松散的）
- "上升"通道要明示：note → kp/case/model/concept 的路径清晰

**示例 wiki**：
- 个人三年读书笔记（200+ 条）
- 个人项目管理笔记（按项目分组）
- 个人日常思考（时间线 + 主题双索引）

### 综合语境

**典型场景**：长期积累的混合内容——既有课程笔记也有个人观察，既有团队方法论也有个人反思

**主目录**：全部并存，按当前资料类型分支

**萃取骨架**：每份资料单独判定子语境

**索引侧重**：多维并存（领域 + 类型 + 时间 + 项目）

**强约束**：
- 必须有清晰的"主题/课程/项目"分类段，让用户能一眼定位
- 通用 note（个人思考）和结构化卡片（kp/case）必须分目录存放（不混在 kps/ 下）

## 主语境切换的处理

wiki 长期维护过程中可能切换主语境：

| 切换 | 处理 |
|:---|:---|
| 个人笔记 → 综合（发现多了结构化笔记） | 把"反复引用的 note"上升为 kp/case；补建 `wiki/concepts/` |
| 课程 → 综合（开始加个人反思） | 新建 `wiki/notes/`，不破坏原有 kps/ |
| 知识库 → 综合（加了案例背后的反思） | 同上 |
| 任意 → 课程（要把笔记整理成课程） | 大规模迁移：note → kp，重新打标签 |
| 课程 → 知识库（不再讲授，转为查阅） | 删除 module 结构，kp 转为 case/concept |

> **默认建议**：建 wiki 时宁可选"综合"，给将来留余地。代价是索引稍复杂，收益是切换成本低。

## 边缘情况

### "我只是想整理一下这份资料"

如果用户的目的只是**整理一份资料**而非建长期 wiki：

1. 问"这份资料后续还会被查阅吗？"
2. 否 → 走 Build 模式快速落骨架，仅做一次 Compile，不建多维索引
3. 是 → 走正常流程，按资料形态选主语境

### "我不知道该选哪种"

引导用户回答第 1 问（谁会用）。如果还是不清楚：

1. 建议"个人笔记"作为起点（最自由，将来可上升）
2. 或建议"综合"（最灵活，将来可分流）

### "我的目录里已经有内容了"

走 Build 模式 B1 现状扫描 + B2 询问用户主语境，按既有内容推断：

| 既有内容特征 | 推断主语境 |
|:---|:---|
| 有 `module/` 目录、有"第 X 讲"命名 | 课程 |
| 有 `concept/` `model/` 目录、无 module | 知识库 |
| 有 `note/` 目录、按日期命名 | 个人笔记 |
| 混合 | 综合 |
